# 0012. REST route design for User Story endpoints

- Status: Accepted
- Date: 2026-06-15
- Deciders: Gutiérrez Soto, Jhosepmyr Orlando

## Context

`UserStory` is a DDD aggregate root inside the `discovery` bounded context. It has two meaningful
parent relationships:

- **`projectId`** — the project it belongs to in the backlog (long-lived ownership).
- **`sessionId`** — the discovery session that originated it (nullable: `null` for manually created
  stories, set for AI-generated ones).

The initial design (following the academic report) scoped all story endpoints under sessions:
`/api/sessions/{sessionId}/stories`. During implementation two problems emerged:

1. **Manual creation has no session.** A user uploading an existing backlog story has no originating
   session; forcing one would be artificial and wrong.
2. **Two distinct client use cases.** Creating/reading stories at the project level (backlog view) is
   a different interaction from reviewing AI-generated stories in the context of a session.

The question was also raised of whether DDD aggregates should dictate REST route structure.

## Decision

**DDD aggregate boundaries do not dictate REST route hierarchy.** Routes are an Interface Layer
concern driven by the client's use case, not by the domain model's consistency boundaries. An
aggregate root's BC ownership does not require a 1:1 mapping to URL nesting.

We define two orthogonal controllers for `UserStory`, following the `{scope}StoryController`
naming convention:

### `ProjectStoryController` — `/api/projects/{projectId}/stories`

Handles **project-level** operations where the project is the natural access context:

| Method | Path | Description                                 |
|--------|------|---------------------------------------------|
| `POST` | `/`  | Manually create a story (no session needed) |
| `GET`  | `/`  | Consolidated project backlog (future)       |

`sessionId` is `null` for manually created stories. The controller lives in the `discovery` BC
because `discovery` owns the `UserStory` aggregate — the URL scope does not determine BC ownership.

### `SessionStoryController` — `/api/sessions/{sessionId}/stories` (future)

Handles **session-level** operations where the session provides authorization and review context:

| Method  | Path                 | Description                            |
|---------|----------------------|----------------------------------------|
| `GET`   | `/`                  | List stories generated by this session |
| `GET`   | `/{storyId}`         | Get a single story with criteria       |
| `POST`  | `/{storyId}/approve` | Approve a story                        |
| `POST`  | `/{storyId}/reject`  | Reject a story                         |
| `PATCH` | `/{storyId}`         | Edit story content                     |

These arrive with their own use-case slices.

## Consequences

**Positive:**
- Manual creation is natural — no artificial session required.
- Controller names are symmetric and self-documenting (`{scope}StoryController`).
- Adding `SessionStoryController` later does not require changing existing routes.
- BC ownership remains clear: both controllers live in `discovery` regardless of URL prefix.

**Negative:**
- The academic report originally modeled all story CRUD under sessions; this diverges from that
  model. The divergence is documented here so reviewers understand the rationale.

**Neutral:**
- The same `UserStory` aggregate is accessible from two URL scopes. This is the standard REST
  pattern for resources with multiple meaningful parent contexts (aliased resources).
