# 0012. REST route design and controller naming convention

- Status: Accepted
- Date: 2026-06-15
- Deciders: Gutiérrez Soto, Jhosepmyr Orlando

## Context

`UserStory` and `DiscoverySession` are DDD aggregate roots inside the `discovery` bounded context.
`UserStory` has two meaningful parent relationships:

- **`projectId`** — the project it belongs to in the backlog (long-lived ownership).
- **`sessionId`** — the discovery session that originated it (nullable: `null` for manually created
  stories, set for AI-generated ones).

The initial design (following the academic report) scoped all story endpoints under sessions:
`/api/sessions/{sessionId}/stories`. During implementation two problems emerged:

1. **Manual creation has no session.** A user uploading an existing backlog story has no originating
   session; forcing one would be artificial and wrong.
2. **Two distinct client use cases.** Creating/reading stories at the project level (backlog view) is
   a different interaction from reviewing AI-generated stories in the context of a session.

A related question arose: should the controller name reflect the bounded context (`DiscoverySession`)
or the URL scope (`project`)?

## Decision

### 1 — DDD aggregate boundaries do not dictate REST route hierarchy

Routes are an Interface Layer concern driven by the client's use case, not by the domain model's
consistency boundaries. An aggregate root's BC ownership does not require a 1:1 mapping to URL
nesting.

### 2 — The `{scope}{Resource}Controller` naming convention

Controllers are named after the **URL scope** (the path segment that acts as the parent context),
not after the bounded context. This keeps the name symmetric with the route and makes intent
immediately clear to a reader.

| Controller                 | Route prefix                         | Resource           |
|----------------------------|--------------------------------------|--------------------|
| `ProjectSessionController` | `/api/projects/{projectId}/sessions` | `DiscoverySession` |
| `ProjectStoryController`   | `/api/projects/{projectId}/stories`  | `UserStory`        |
| `SessionStoryController`   | `/api/sessions/{sessionId}/stories`  | `UserStory`        |

BC ownership remains clear — all three controllers live in the `discovery` package regardless of URL
prefix.

### 3 — Two orthogonal scopes for `UserStory`

#### `ProjectStoryController` — `/api/projects/{projectId}/stories`

Handles **project-level** operations where the project is the natural access context:

| Method | Path         | Description                                 |
|--------|--------------|---------------------------------------------|
| `POST` | `/`          | Manually create a story (no session needed) |
| `GET`  | `/{storyId}` | Get a single story                          |
| `GET`  | `/`          | Consolidated project backlog (paginated)    |

`sessionId` is `null` for manually created stories.

#### `SessionStoryController` — `/api/sessions/{sessionId}/stories`

Handles **session-level** operations where the session provides authorization and review context.
Only stories with a matching `sessionId` are visible here — manually created stories (null
`sessionId`) are excluded:

| Method  | Path                 | Description                                        |
|---------|----------------------|----------------------------------------------------|
| `GET`   | `/{storyId}`         | Get a story generated by this session              |
| `GET`   | `/`                  | List stories generated by this session (paginated) |
| `POST`  | `/{storyId}/approve` | Approve a story (future)                           |
| `POST`  | `/{storyId}/reject`  | Reject a story (future)                            |
| `PATCH` | `/{storyId}`         | Edit story content (future)                        |

## Consequences

**Positive:**
- Controller names are symmetric and self-documenting (`{scope}{Resource}Controller`).
- Manual creation is natural — no artificial session required.
- `SessionStoryController` hides manual stories by design, reducing noise during review.
- Adding future controllers does not require changing existing routes.
- BC ownership remains clear regardless of URL prefix.

**Negative:**
- The academic report originally modeled all story CRUD under sessions; this diverges from that
  model. The divergence is documented here so reviewers understand the rationale.
- `ProjectSessionController` loses the "Discovery" prefix — readers must know the `discovery`
  package to infer the BC.

**Neutral:**
- The same `UserStory` aggregate is accessible from two URL scopes. This is the standard REST
  pattern for resources with multiple meaningful parent contexts (aliased resources).
